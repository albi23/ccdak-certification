## Kafka Producer Configurations

Kafka producers send records to topics. The efficiency, reliability, and performance of data production can be significantly influenced by how producers are configured.

### Key Points for CCDAK on Producers

- **Efficiency and Throughput**: Configurations like batch size and compression type can greatly affect the throughput.
- **Data Integrity**: Settings such as `acks` and `retries` ensure data integrity and delivery guarantees.
- **Latency**: Configurations like `linger.ms` can be tuned to balance between latency and throughput.
- **Reliability**: Features like idempotence and transactions ensure reliable data delivery.
- **Simplicity:** Producers are conceptually simpler than consumers since they do not require group coordination.
- **Broker and Partition Awareness:** Producers automatically know which broker and partition to write to.
- **Partitioning:** A producer partitioner maps each message to a topic partition, and the producer sends a produce request to the leader of that partition.
- **Message Key Guarantee:** The partitioners shipped with Kafka ensure that all messages with the same non-empty key are sent to the same partition.
- **Keyless Sending:** If producers send data without a key, the default partitioner spreads records across partitions (sticky partitioning since 2.4: stays on one partition until the batch is full, then switches; older versions used round-robin).
- **Acknowledgements:** Producers can choose to receive acknowledgements of data writes.

### Important Producer Properties

#### `acks`
- **Default**: all (changed from 1 in Kafka 3.0)
- **Description**: The number of acknowledgments the producer requires from brokers. Options are 0, 1, or 'all' (-1). With `all`, `min.insync.replicas` on the broker/topic sets the minimum ISR size for a write to succeed.
- **Trade-offs**: More `acks` increase reliability but may reduce throughput.

#### `linger.ms`
- **Default**: 5 (ms; was 0 before Kafka 4.0)
- **Description**: The delay to aggregate batches of records. Higher values allow larger and more efficient batches.
- **Trade-offs**: Increases latency but improves throughput and efficiency.

#### `batch.size`
- **Default**: 16384 (16KB)
- **Description**: Maximum batch size in bytes. Larger batches are more efficient but take more memory and may delay transmission.
- **Trade-offs**: Balances memory usage with throughput.

#### `max.in.flight.requests.per.connection`
- **Default**: 5
- **Description**: The maximum number of unacknowledged requests the client will send on a single connection before blocking.
- **Trade-offs**: Higher values can improve throughput but may compromise ordering when retries are used without idempotence (with idempotence ordering is kept up to 5).

#### `enable.idempotence`
- **Default**: true (since Kafka 3.0; requires `acks=all`, `retries>0`, `max.in.flight.requests.per.connection<=5`)
- **Description**: Prevents duplicate records caused by retries (exactly-once per partition within a producer session) and preserves ordering.
- **Trade-offs**: May slightly impact throughput but significantly increases reliability.

#### `compression.type`
- **Default**: none
- **Description**: The compression type for all data generated by the producer. Options are `none`, `gzip`, `snappy`, `lz4`, and `zstd`.
- **Trade-offs**: Compression reduces the size of data sent over the network at the cost of CPU usage.

#### `retries`
- **Default**: 2147483647 (Integer.MAX_VALUE)
- **Description**: Number of retries on transient errors. In practice bounded by `delivery.timeout.ms`.
- **Trade-offs**: Ensures delivery. May reorder or duplicate records if idempotence is disabled and `max.in.flight.requests.per.connection` is greater than 1.

#### `delivery.timeout.ms`
- **Default**: 120000 (2 minutes)
- **Description**: Upper bound on the time between `send()` returning and success/failure being reported. Must be >= `linger.ms + request.timeout.ms`.

#### `request.timeout.ms`
- **Default**: 30000 (30 seconds)
- **Description**: Maximum time the producer waits for a response to a single request.

#### `max.block.ms`
- **Default**: 60000 (1 minute)
- **Description**: How long `send()` blocks when the buffer is full or metadata is unavailable before throwing `TimeoutException`.

#### `transaction.timeout.ms`
- **Default**: 60000 (1 minute)
- **Description**: Maximum time a transaction can remain open. Relevant for exactly-once semantics.
- **Trade-offs**: Longer transactions can hold resources but ensure completeness of operations.

#### `max.request.size`
- **Default**: 1048576 (1MB)
- **Description**: The maximum size of a request (and so of a record batch/message). The broker/topic limits `message.max.bytes`/`max.message.bytes` also apply.
- **Trade-offs**: Larger sizes can improve throughput but risk overwhelming brokers or dropping connections on large messages.

#### `buffer.memory`
- **Default**: 33554432 (32MB)
- **Description**: Total memory available to the producer for buffering. When exhausted, `send()` blocks up to `max.block.ms`.
- **Trade-offs**: More memory allows more batching and in-flight messages, improving throughput but increasing memory usage.

#### `transactional.id`
- **Default**: null
- **Description**: Unique identifier for transactional messages. Necessary for exactly-once semantics.
- **Trade-offs**: Enables transaction support at the cost of additional overhead for maintaining state.

### Handling Errors in Kafka Producers

Kafka classifies errors as *retriable* or *non-retriable*, affecting how producers react to them.

#### Retriable Errors
Retriable errors are temporary and often resolved through retries. Kafka producers automatically retry these errors until the `retries` limit or `delivery.timeout.ms` is reached. Common retriable errors include:

- **Leader Not Available**: Occurs when a new leader is being elected. The producer automatically recovers.
- **Not Leader for Partition**: The targeted leader is not the current leader for the partition. The producer automatically recovers.
- **Not Enough Replicas**: Not enough replicas are available for the producer to satisfy the `acks` configuration.

Producers handle these errors by:
- Retrying with a delay specified by `retry.backoff.ms`.
- Continuing retries until `retries` or `delivery.timeout.ms` is exhausted, then failing the send.

#### Non-Retriable Errors
Non-retriable errors indicate issues not resolved by retrying and often require configuration changes or other interventions:

- **Record Too Large**: The record size exceeds `max.request.size` (or the broker/topic message size limit). Requires adjusting the message size or configuration.
- **Invalid Topic Exception**: The specified topic name is invalid.
- **Topic Authorization Failed**: The producer lacks permission to publish to the specified topic.
- **Serialization Exception**: The key or value could not be serialized.
- **Broker Not Available**: The broker is not available for connections.
- **Invalid Required Acks**: The `acks` configuration is set to an invalid value.

Non-retriable errors demand an intervention or change in configuration or permissions. They point to conditions that retries alone cannot overcome, often requiring administrative action or code changes.

Handling non-retriable errors requires:
- Catching and logging the exception.
- Reviewing the error to understand its cause.
- Adjusting the configuration or addressing the permission issues as needed.

#### Best Practices for Error Handling
- **Monitoring**: Continuously monitor log files for error patterns to proactively address emerging issues.
- **Smart Retrying**: Use the `retry.backoff.ms` setting wisely to avoid overwhelming the system.
- **Idempotent Producers**: Enable `enable.idempotence` to ensure that messages are not duplicated in the event of retries.


## Delivery Guarantees (producer side) (CCDAK)

| Guarantee | Producer settings |
|---|---|
| **At-most-once** | `acks=0` or `retries=0` — no retry, message may be lost, never duplicated |
| **At-least-once** | `acks=all` (or 1) + retries (default) — never lost on retriable errors, but retries can create **duplicates** (and reordering without idempotence) |
| **Exactly-once (per partition, per session)** | `enable.idempotence=true` (default since Kafka 3.0; requires `acks=all`, `retries>0`, `max.in.flight<=5`). Broker de-duplicates using producer id (PID) + per-partition sequence number |
| **Exactly-once across topics/partitions** | Idempotence + **transactions**: `transactional.id`, `initTransactions()`, `beginTransaction()`, `send()`, `sendOffsetsToTransaction()`, `commitTransaction()` / `abortTransaction()` |

- Transactions are atomic over multiple partitions and the consumed offsets (consume-transform-produce loop). Consumers must use `isolation.level=read_committed`. Same `transactional.id` after a restart **fences** the old (zombie) producer (`ProducerFencedException`).
- `acks=all` durability also needs `min.insync.replicas>=2` and `replication.factor>=3`. Otherwise `NotEnoughReplicasException`.

## Partitioner (CCDAK)

- The **partitioner** decides which partition of the topic a record is sent to. Called inside `send()` before batching.
- **Default behaviour:**
  1. **Partition explicitly set** in `ProducerRecord` → used as-is.
  2. **Key not null** → `partition = toPositive(murmur2(keyBytes)) % numPartitions`. Same key → same partition (as long as the partition count doesn't change!), giving per-key ordering.
  3. **Key null** → **sticky** behaviour: the producer sticks to one partition until the batch is full (`batch.size`) or `linger.ms` expires, then switches (Kafka ≥ 2.4 sticky; ≥ 3.3 built-in uniform sticky/adaptive). Older versions used round-robin per record.
- Custom partitioner: implement `org.apache.kafka.clients.producer.Partitioner` and set `partitioner.class` (e.g. to route a hot key or VIP customers to a dedicated partition).
- **Adding partitions** to a topic changes `hash % numPartitions` → same key may land on a different partition. Ordering per key is broken across the change.
- The partitioner only chooses the partition. The **leader of that partition** receives the data.
- Hot keys (skewed key distribution) lead to uneven partitions.

## Serialization (CCDAK)

- `key.serializer` and `value.serializer` are **required** producer configs. The broker only stores `byte[]`.
- Built-in: `StringSerializer`, `IntegerSerializer`, `LongSerializer`, `DoubleSerializer`, `ByteArraySerializer`, `UUIDSerializer`, `ByteBufferSerializer`, `VoidSerializer`. Avro/Protobuf/JSON-Schema via Schema Registry (`KafkaAvroSerializer`, etc.).
- Custom serializer: implement `Serializer<T>` (`byte[] serialize(String topic, T data)`). Consumers must use the matching deserializer.
- A mismatch (e.g. producer `StringSerializer`, consumer `IntegerDeserializer`) → `SerializationException` on the consumer.
- Common data formats: **String/JSON** (human readable, no schema enforcement, larger), **Avro** (compact binary, schema in Schema Registry, best evolution support), **Protobuf**, **JSON Schema**, raw bytes. Prefer a schema-based format for contracts between teams.

## Record Headers (CCDAK)

- Headers are **key (String) → value (byte[])** pairs attached to a record, **separate from key and value**: `record.headers().add("trace-id", bytes)`. Read with `record.headers().lastHeader("trace-id")`.
- Available since Kafka 0.11. Headers are **not** used for partitioning or compaction and are **not** part of the key.
- Design: use for **metadata** — tracing/correlation IDs, source system, content type, schema/version, routing hints, audit info — so the payload stays untouched and consumers can filter or route without deserializing the value.
- Keep them small (they count toward message size). Duplicate header keys are allowed (order preserved).
- Kafka Connect: SMTs `InsertHeader`, `HeaderFrom`, `DropHeaders`. DLQ can add error context headers.
- Console consumer: `--property print.headers=true`.

## Key Design for Partition Strategy (CCDAK)

- Same key ⇒ same partition ⇒ **ordering guaranteed per key** only (not per topic).
- Choose a key with **high cardinality and even distribution** (e.g. `customerId`, `orderId`). Avoid skewed keys (country, boolean) → hot partitions.
- Need ordering across entities → use a common key (e.g. all events of an account use `accountId`).
- No ordering needed → null key for best distribution.
- Compacted topics **require** a non-null key.
- Plan the partition count up front: changing it later remaps keys.
